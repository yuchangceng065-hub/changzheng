## 一、技术栈（需求「二、技术栈建议」）

| 需求建议 | 实际采用 | 说明 |
| --- | --- | --- |
| 前端框架：Vue 3 或 React | **Vue 3.5**（`<script setup>` 组合式 API） | 选 Vue 3，与需求建议一致 |
| 地图渲染：ECharts Geo 或 Leaflet | **ECharts 5 Geo 组件** | `geo` + `lines`（路线）+ `effectScatter`（节点/起点） |
| UI 组件库：Tailwind / Element Plus / Ant Design | **Tailwind CSS 4** + 自定义设计令牌 | 高度定制的地图叙事界面，工具类负责布局，语义化类负责视觉 |
| 动效：GSAP 或 Framer Motion | **ECharts 原生动画 + CSS 关键帧** | 地图节点动画由 ECharts 的 `effect`/`rippleEffect` 驱动；界面过渡用 CSS，避免为一个动效引入额外运行时依赖 |
| 数据格式：JSON（存储四支队伍的历史节点数据） | **JSON / ESM 模块** `src/data/armies.js` | 四支部队节点数据集中存放 |

### 3.2 地图主交互界面（行军过程）

> **与需求的偏差（已如实说明，共三处）**
>
> 1. **音效未实现**：需求提到「触发动画/音效」，本作品实现了动画，但**未加入音效**。原因是浏览器自动播放策略会拦截未经用户手势的音频，且科普作品中突兀的音效反而干扰阅读。如需补齐，建议在顶栏加一个默认关闭的音效开关。
> 2. **难度星级已全部移除（按作者要求）**：需求 3.1／3.2 要求四支部队卡片与顶部状态栏展示**难度星级**（★★★★★ 等），节点详情卡展示**行军艰难程度**。按作者要求现已**全部移除**，理由是「每支部队的行军过程都是艰难的，不可量化」。
>    连带影响：需求给定的引导语后半句「难度星级代表当年行军的艰险程度，并非部队作战强弱」因星级不存在而失去指代对象，**一并删除**（原句记录在 `src/data/specNotes.js`）。
>    底层数据（`armies.js` 的 `hardship`、`stars` 字段）**均未删除**，恢复界面与文案的成本很低。
>    **这是与需求文档最明显的一处不一致，特此记录。**
> 3. **起点点击行为改为直接进入（按作者要求）**：需求 3.1 要求「用户点击起点图标，弹出选择卡片」。现按作者要求改为**点击起点标记直接选中该部队并进入故事**，不弹确认卡片；「选择卡片」的职责由左侧选部队浮窗承担。**此项与需求文档不一致，特此记录。** 如需恢复原流程（点击起点 → 弹卡片 → 点按钮进入），改动量很小。

### 3.4 沉浸感增强（配图 / 播放节奏 / 主题配色 / 小游戏预留）

| 需求条目 | 实现位置 | 具体做法 |
| --- | --- | --- |
| **大事件配图** | [EventArtwork.vue](src/components/EventArtwork.vue)、[artwork.js](src/data/artwork.js) | 12 个**手绘内联 SVG 场景**：出发、抢渡江河、铁索桥、雪山、草地、重要会议、胜利会师、民族团结、鏖战关隘、回旋运动战、行军、长征胜利。归属按两级决定：先查具体节点（如飞夺泸定桥→铁索桥），再按节点类型兜底（battle→关隘、crossing→渡河……），因此新增节点无需逐个配图。**改用真实照片只需给节点加 `photo` 字段**（图片放 `public/art/`），组件会自动优先渲染照片、回退插画 |
| **播放节奏可控** | [App.vue](src/App.vue) 的 `SPEEDS` | **进入部队故事时默认暂停**，停在出发地等读者按「继续」——一进来就自动开走会让人来不及看清起点与部队概况；速度默认「慢」3.2 秒/站（原 1.25 秒太快，来不及读事件卡与配图），可切「中」2.1 秒 /「快」1.2 秒；播放中切换速度立即生效，无需先暂停 |
| **主题配色** | [style.css](src/style.css) | 由蓝黑基调改为**红黑基调**：多层红色径向光叠加在暗红底上，呼应“星火/红旗”意象；地图要素保持冷色，靠色相差异保证省份边界与文字可读性 |
| **小游戏预留** | [MiniGameHost.vue](src/components/MiniGameHost.vue)、[miniGames.js](src/data/miniGames.js) | **本版本不实现玩法**，只预留 4 个接入点（抢渡金沙江 / 飞夺泸定桥 / 穿越草地 / 四渡赤水）、玩法类型分类，以及 `emit('finish', { passed, score })` 结果接口。把对应条目的 `implemented` 改为 `true`，界面上的“开发中”占位会自动变成可进入状态 |

> **配图为什么是手绘 SVG 而不是照片**：本作品不使用外部图片资源——离线可用、无版权与来源风险、随主题统一、任意缩放不失真。若日后要换成史料照片或美术稿，`photo` 字段的口子已经留好，不需要改动组件逻辑。

### 3.6 全站页面结构（导航 + 五个页面）

需求文档只描述了「选择部队 → 地图行军」这条主线。作品在此基础上补了一层**全站导航**，把内容按主题拆成独立页面：

| 页面 | 内容 | 实现 |
| --- | --- | --- |
| **首页** | 作品标题、长征总述、四个入口卡片、关键数字 | `views/HomeView.vue` |
| **部队介绍** | 四路红军逐一说明：番号、出发地/日期、终点/日期、历时、行程、兵力、途经省份、概述、关键事件标签，并可**直接进入该部队的地图** | `views/ArmiesView.vue` |
| **深度交互** | 选择部队 → 地图逐站推进 → 节点详情（原主线界面） | `App.vue` 的 journey 分支 + `MapStage.vue` |
| **长征图集** | 按事件编排的图集，含大图查看；条目引用历史节点 id，因此**直接复用配图场景与真实图片通道**，换成真实照片无需改代码 | `views/GalleryView.vue` + `data/gallery.js` |
| **长征精神** | 长征精神的五条权威概括，每条对应四路红军的真实经历；附来源注记 | `views/SpiritView.vue` |

导航栏见 `components/NavBar.vue`（首页 / 部队介绍 / 深度交互 / 长征图集 / 长征精神 + 资料来源与注记）。
页面切换用组件内的 `view` 状态实现，**未引入 vue-router**——只有五个页面、无嵌套路由与深链接需求，加一个依赖不划算。

> 命名说明：这一栏最初叫「长征游戏」，按作者意见改为「**深度交互**」。理由是「游戏」一词与党史科普的严肃调性不符，容易被误读为娱乐化；这一栏的实质也确实是"逐站推进 + 查阅史实"的深度交互，而非游戏。节点卡里预留的互动入口同步由「玩法开发中」改为「互动内容开发中」。

> 视觉上刻意**不使用 emoji 图标**：节点类型改用两字中文标签（会议／战斗／渡河／雪山／草地／会师…），进度轨道改用**站点序号**，图集与按钮只用文字。装饰元素一律改为排版手段（字重、字距、留白、细分隔线）。

### 3.7 线路内容校订（依据作者提供的路线大事记）

线路内容已按作者提供的《四路主力红军完整长征路线大事记》（权威党史定本体系）**逐条校订并大幅扩充**：

| 部队 | 校订前 | 校订后 | 主要补充 |
| --- | --- | --- | --- |
| 红一方面军 | 21 | **37** | 第二、三道封锁线、通道／猴场会议、南渡乌江、佯攻贵阳、威逼昆明、会理会议、两河口／芦花／沙窝／毛儿盖会议、包座战斗、巴西会议、俄界会议、榜罗镇会议 |
| 红25军 | 8 | **12** | 花山寨会议、鄂豫陕边游击战争、沣峪口会议、西进甘肃、永宁山 |
| 红二、六军团 | 12 | **17** | 石阡会议、盘县会议、挺进滇中、中甸休整、甲洼会师、绒坝岔会师、成徽两康战役 |
| 红四方面军 | 15 | **24** | 涪江流域作战、土门战役、绥崇丹懋战役、天芦名雅邛大战役、百丈关战役、再次翻越大雪山、转战西康、岷洮西战役、通庄静会战役、山城堡战役 |
| **合计** | 56 | **90** | 重大事件基本全收录 |

**几处关键更正**：

1. **红一方面军的出发是两件事**：原数据把「1934.10.10 出发」与「于都出发」混为一谈。据大事记，10 月 10 日是中共中央、中革军委机关**由瑞金出发**，10 月 17 日才是主力从**于都河**渡河启程。现拆为两个节点；`startPoints()` 也改为定位到「出发地」对应的节点而非 `nodes[0]`，保证首页浮窗落在**于都**。
2. **四渡赤水是四个不同事件**：原数据合成一个节点。据大事记，一渡（土城、元厚 1.29）、二渡（太平渡、二郎滩 2.18—21）、三渡（茅台 3.16—17）、四渡（二郎滩、太平渡 3.21—22）渡口与时间各不相同，现拆为四个节点，并补入「遵义战役·娄山关」（2.25—28）。
3. **红四方面军的行军不止到会宁**：据大事记，会宁会师（10.9）之后还有山城堡战役（11.21—22，大事记称之为「长征胜利结束前的最后一仗」）与 12 月 2 日红军总部到达保安，故末节点为「保安会合」。
4. **红四方面军的起点**：大事记把 1935 年 2 月的陕南战役列在强渡嘉陵江之前。陕南战役属于长征的前置策应（需求与备注文案均以「1935.3 强渡嘉陵江」为长征起点），故**不单列节点**，其史实写入「强渡嘉陵江」的详细正文。

**自检脚本相应做了三处精化**（`scripts/check-data.mjs`）：

1. **出发节点断言放宽为「必须存在且不能靠后」**：原断言要求 `nodes[0].kind === 'start'`，但红25军的花山寨会议（11.11 决定战略转移）按时间本就在何家冲出发（11.16）之前，故改为「必须有且仅有一个 start 节点，且位置不在前两位之后」。
2. **红四方面军会宁会师改为「节点必须存在」**：原断言要求末节点地点含「会宁」，与大事记延续到保安的记录冲突。
3. **新增交叉引用校验**：`ART_BY_NODE`、`MINI_GAME_BY_NODE`、`public/art/manifest.json` 里引用的节点 id 必须真实存在。此前 `r1-chishui` 拆成 `r1-chishui1..4`、`r4-cangxi` 改名后共有**三处引用静默失效**（不报错，只是配图退化成默认场景、小游戏不再出现），该检查已能自动拦截。

> ⚠ **一处需要作者确认的不一致**：这份大事记里**是带难度星级的**（红一方面军 ★★★★★、红25军 ★★★☆、红二、六军团 ★★★★、红四方面军 ★★★★☆），与作者此前「删除星级，过程艰难不可量化」的要求相反。目前仍按作者要求**不展示星级**，数据里的 `stars` 字段保留原值，随时可以恢复。

> **标记锚点（一个容易踩的通用坑）**
>
> 地图标记是「图形 + 文字标签」的组合。若把两者放进同一个容器、再用 `translate(-50%, -50%)` 居中，**居中的是两者整体**，图形就会被文字挤偏——标签越长偏得越多；标签显隐切换时图形还会明显跳动。
>
> 正确做法是**让图形本身成为锚点**：
> - **历史节点标记**：按钮做成固定 22×22 的锚点盒、居中于坐标，圆点用 grid 居中其中，名称标签改为**绝对定位**挂在盒子右侧。这样标签的显隐与长短都不影响圆点位置。
> - **起点胶囊**：胶囊本身较宽，改用 `translate(-14px, -50%)` 把「圆点中心」对到坐标上（14px = 边框 1px + 左内边距 4px + 圆点半径 9px）。
>
> 这个问题由作者在实际使用中发现：选中节点后名称标签出现，圆点随之偏移。**修复前，圆点在显示标签时会偏出约半个标签宽度**（十几到几十像素，取决于标签长短）。

按作者要求适度加入国旗与党徽，**遵循《国旗法》《中国共产党党徽党旗条例》的使用规范**：

| 标识 | 位置 | 实现 | 规范符合性 |
| --- | --- | --- | --- |
| **中华人民共和国国旗** | 顶部导航的品牌标识；首页标题上方的引题行 | `components/FlagCN.vue`，**按标准规格几何绘制** | ✅ 旗面严格 3:2；大星中心 (5,5)、外接圆半径 3，四小星中心 (10,2)、(12,4)、(12,7)、(10,9)、半径 1，各有一角正对大星中心；配色取标准数字色值（红 #EE1C25、黄 #FFDE00）。**未做任何近似或变形** |

**使用原则：适度、规范、不娱乐化**

- **不滥用**：全站只出现两处，不做满屏装饰；
- **不变形**：国旗保持 3:2，党徽等比缩放，不拉伸、不旋转、不加滤镜与动效；
- **不商用**：本作品为非商业性科普作品，标识不用于商标、广告等法规禁止的用途；
- **可替换**：党徽做成独立组件，替换官方矢量图只需改一个文件，使用处（红底、尺寸、圆角）无需改动。

**图形正确性做过实际核对**（不是"看着差不多"）：

- `scripts/preview-symbols.py` 用 Pillow **按组件里同一套几何参数**把两个标识栅格化成 PNG（与 SVG 共用同一份星位与弧线参数），逐像素检查；
- 国旗核对结果：旗面 3:2、大星与四小星的位置与朝向均符合规格；
- 党徽核对结果：初版镰刀刀身用等宽圆弧描边，看起来只是一个弯钩；改用"外弧半径 40 + 内弧半径 56"的月牙形填充后具备刀刃形态；进一步按像素扫描发现刀身末端收成针尖处会被抗锯齿吃掉、与刀柄之间留下 6—14 像素的可见断口，于是把末端改为约 6 个单位宽的**钝口**，刀柄从钝口接出，断口消除。
- 该脚本保留在 `scripts/preview-symbols.py`，替换官方党徽后可再跑一次复核。



需求文档描述的是「地图主交互界面」，实现时进一步做了叙事化改造，让地图从"主角"变成"坐标指示器"，把屏幕交给故事：

| 设计 | 做法 |
| --- | --- |
| **开始界面** | 地图**铺满整屏**作为底，取景范围框定为**大陆 + 台湾 + 海南岛**（`HOME_BOUNDS`，北纬 17.5° 以北）——若不裁掉南海深处，地图会被纵向拉得很长、大陆变得很小；四个起点以脉冲标记标出；左上角一个**可收起的小浮窗**列出四支部队供选择；点击地图上的起点则弹出该部队卡片；底图声明条位于地图**右下角** |
| **地图与故事各占一半** | 选定部队后进入故事模式：地图列与故事列各 `1fr`，左右各半屏 |
| **固定视野 + 固定视角** | 故事页地图与故事列**各占一半**（`1fr 1fr`）。地图取景到以武汉一带为中心的「汉地十八省 + 四川」（`JOURNEY_BOUNDS` = 98–126°E / 20–44°N，中心 112°E），四支部队路线（99.7–115.4°E）都完整落在框内，若个别路线超出则由 `unionBounds` 自动扩边。中心不取武汉本点（114.3°E），否则最西端的甘孜、中甸（约 99.7°E）会贴边。**取景方式：实测自校正 + 强制重排**（`MapStage.vue` 的 `frameTo()` / `scheduleFrame()`）——先用 `center` 摆正视窗中心，再用 `convertFromPixel` 读出画布四角当前对应的真实经纬度，以「当前跨度 ÷ 目标跨度」反算 `zoom` 写回模型；**设完必须主动 `chart.resize()` 强制重排一次**，因为 `setOption` 只是把 center/zoom 写进模型，真正读取它们的是 `resizeGeo`（只在坐标系重建时执行），不强制重排会表现为"刚进去位置不对、随便动一下就跳正"；取景结束后还要重算 HTML 起点标记的像素位置，否则小浮窗会整体偏移。**`geo.boundingCoords` 已弃用**（它只决定缩放基准、决定不了视窗中心）。**缩放与拖动已开放**（`roam: true`）：标记位置由 HTML 覆盖层自行换算，不受漫游影响。切换部队时**销毁并重建图表实例**（`dispose()` + `init()`）|
| **头图收窄并与导语并排** | 图片不再是整幅卡片宽度铺开，而是固定占左侧一栏（最大 340px，约 340×191），右侧放导语与数据格；窄屏（≤720px）自动改为上下堆叠，把横向空间让给介绍文字 |
| **导航集中在顶栏** | 「← 上一站 / 前进一站 / 直达终点 / 重走」等推进操作全部集中在故事区顶栏的状态条里；事件卡内**不再重复放导航按钮**——原先卡片底部的「继续前进 →」与顶栏「前进一站」功能重复，已按作者要求删除 |
| **底部节点轨道** | 竖排时间线换成**横向进度轨道**（`NodeRail.vue`），常驻故事区底部、可横向滚动、当前站点自动滚入视野 |
| **说明文字外移** | 地图收窄后不再在地图内叠加里程提示与底图声明（会盖住地图），统一移到故事区页脚一行显示 |
| **移动端** | 地图收到 34vh，故事区随后展开、由页面整体滚动；选择模式浮窗改为贴底 |

> 注：`src/components/TimelineStrip.vue`（原竖排时间线）已被 `NodeRail.vue` 取代，保留在仓库中但不再引用，可安全删除。
>
> ⚠ **领土表示的可见性说明（重要，与下方「无领土争议问题」一条相关）**：底图数据本身**完整包含**台湾省、海南省域、南海诸岛与九段线（`analyzeIntegrity` 四项客观检测均通过），但为了画面可读性，**开始界面与故事界面的取景范围都裁在南海之外**——开始界面只到北纬 17.5°，故事界面只框住长征路线。因此**南海诸岛与九段线在界面上不可见**。

## 四、验收命令

```bash
node scripts/check-data.mjs   # 史实数据自检（含需求专项断言）
node scripts/fetch-basemap.mjs # 获取底图并做合规自检（仅用于本地预览）
node scripts/verify.mjs       # 端到端交付校验
pnpm build                    # 生产构建
pnpm preview                  # 预览构建产物
```

`scripts/verify.mjs` 中的底图自检调用的是**与浏览器完全相同**的 `analyzeIntegrity` 逻辑，因此命令行结论与界面告警必然一致，不会出现「脚本说合规、页面却在报警」的矛盾。
